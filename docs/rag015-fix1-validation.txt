Some loads of the same model file initialised "speculative decoding context initialized" and
"the context supports bounded partial sequence removal"; most did not ("the context does not
support partial sequence removal", no speculative context). The engine path for this model was
inconsistent between loads, and every healthy answer of the session came from the earlier
server process (started before 21:34).

Recovery
--------
Unloading and reloading the model did not help (every reload produced a fresh but still
degenerate runner); unloading every model did not help; freeing VRAM (killing an orphaned
llama-server holding 19 GB on GPU0 and 17 GB on GPU1) did not help. Restarting the Ollama
*server process* fixed it immediately. The model blob is unchanged (written 2026-10-06), so no
model file changed.

Retry behaviour through the real UI (driven in a browser, one failure at a time)
--------------------------------------------------------------------------------
The proxy in front of Ollama was stopped so a turn would fail for a transport reason, then
started again to retry it. This also shows that a transport failure is *not* auto-retried.

1. Send while Ollama is unreachable
   conversation: user turn added, no assistant turn
   notice      : "The model could not answer"
                 "Ollama said: could not reach the model server at http://127.0.0.1:11500:
                  ConnectionError: ... [WinError 10061] No connection could be made ..."
                 "Your message is saved; retrying answers that same message - it is never
                  sent twice."
   action      : [Retry this turn] button
   stored      : one user message (the failed turn) - not two

2. Reload the page with that unanswered turn stored
   notice      : "This message has no answer yet"
                 "The last turn did not produce an answer. Retry answers this same message;
                  it is never sent twice."
   action      : [Retry this turn] button
   (the message is not re-typed and not re-sent: the button is the only affordance offered)

3. Press Retry (proxy back up)
   result      : HTTP 200, assistant answer written for the *existing* user turn
   stored      : user, assistant, user, assistant - one user message per turn
   context     : num_ctx 262144 on every assistant turn, generation_retries 0
   notice      : cleared

4. Press Retry again on an answered turn
   result      : 409 {"error": {"kind": "nothing_to_retry",
                                "title": "There is no unanswered message"}}

Two UI defects found by driving the real interface and fixed in the same change:
  * a notice without an action button rendered the text "null" (a null child passed to
    replaceChildren), and
  * opening a chat cleared the "no answer yet" notice immediately after rendering it, so the
    Retry affordance only appeared on the failed turn, not on a reopened chat.
