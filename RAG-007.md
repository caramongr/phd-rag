Project: PhD Academic RAG
Task ID: RAG-007
Goal: Implement academic-aware text normalization and structure-preserving chunking while retaining exact document/page/section/provenance information.
RAG-001 through RAG-006 are complete.
Do not implement embeddings, Qdrant, retrieval, reranking, generation, citation rendering, UI, or LLM-based chunking.
Project root:
F:\phd-rag

Inspect the existing parsing, metadata and domain models before changing anything.
1. Core principle
Chunking must optimize retrieval without destroying evidence provenance.
Every final chunk must allow us to answer:
Which logical document did this come from?
Which physical source file?
Which page(s)?
Which section / heading path?
Was the text native PDF text or OCR?
What content type is it?
Is it scholarly evidence, author work, guidance, supervision or another corpus role?

A chunk must never become anonymous text.
2. Inputs
Use the existing parsed representations from:
PDF
DOCX
Markdown

Preserve integration with:
RAG-002 logical document / hash deduplication
RAG-003 structural parsing
RAG-004 PDF page provenance
RAG-005 OCR provenance
RAG-006 academic metadata

Do not re-parse files independently if an existing parser already supplies the required information.
3. XLSX

Headings should normally provide structure to the following content rather than become isolated retrieval chunks.
6. Normalization philosophy
Normalize for retrieval, but preserve meaning.
Allowed:
Unicode normalization
line-ending normalization
whitespace normalization
dehyphenation where clearly caused by line wrapping
joining wrapped prose lines
removal of repeated page headers/footers when confidently detected
normalization of non-breaking spaces

Not allowed:
rewriting sentences
grammar correction
summarization
paraphrasing
spelling correction
LLM cleanup
removing citations from prose
changing terminology
translating text

Raw extracted text must remain available separately from normalized retrieval text.
7. Hyphenation
Be conservative.
Join:
educa-
tion

into:
education

only when the hyphen appears to be caused by a line/page wrap.
Preserve genuine compounds:
AI-based
higher-order
real-time

Do not use a dictionary or LLM.
Add tests for genuine and false hyphenation cases.
8. Page boundaries
Page provenance must survive chunking.
A chunk may cross a page boundary when necessary for semantic continuity, but it must record:
page_start
page_end

and the underlying source locators.
Prefer not to cross more pages than necessary.
Do not create arbitrary page-sized chunks simply because the input is PDF.
9. Section-aware chunking
Primary chunk boundaries should follow academic structure:
heading
subsection
paragraph
table
page only as provenance, not the main semantic unit

Use the existing explicit/inferred heading information.
Preserve:
section_title
heading_path

Example:
4 Virtual Reality in Higher Education
  4.2 Educational Applications
    4.2.1 Medical Training

A chunk under 4.2.1 should carry the full heading path where available.
10. Target chunk size
Default target:
approximately 700–1000 tokens

Soft target, not a rigid fixed window.
Hard maximum:
1200 tokens

A temporary extension to:
1500 tokens

is acceptable only when splitting would badly damage a coherent structure such as a table or tightly connected section.
Report all chunks exceeding 1200 tokens.
No chunk may exceed 1500 tokens.
11. Token counting
Do not depend on the final generation model tokenizer yet.
Use a deterministic tokenizer/counting strategy suitable for chunk sizing.
Prefer an installed open tokenizer if already available and lightweight.
If introducing a dependency, justify it.
The tokenizer must work offline.
Record:
token_count

on every chunk.
Do not use character count as if it were token count.
12. Paragraph integrity
Prefer:
whole paragraphs

over arbitrary token windows.
Accumulate paragraphs until near the target.
If adding the next paragraph would exceed the hard maximum, start a new chunk.
Only split inside a paragraph when a single paragraph itself exceeds the hard maximum.
For oversized paragraphs, split at:
sentence boundaries

before falling back to a harder split.
13. Overlap
Do not use blind fixed overlap such as:
previous 200 tokens copied into every next chunk

This creates duplicates and retrieval noise.
Instead use structural context.
Every chunk should already carry:
section title
heading path
document metadata reference

If limited overlap is still necessary for an oversized paragraph split, keep it small and explicitly mark it.
Default paragraph-level chunking should have:
overlap = 0

14. Short sections
Do not create tiny chunks just because there is a heading.
A section such as:
4.2 Ethics

AI raises several concerns...

with only 100–200 tokens may be merged with an adjacent section only when semantically safe.
Prefer merging short material within the same parent section.
Do not merge unrelated sibling topics merely to reach a token target.
15. Headings in chunk text
Do not rely solely on metadata fields.
Construct retrieval text so the immediate academic context can be represented when useful.
For example:
[Section: 4.2 Educational Applications > Medical Training]

Actual body text...

But distinguish:
raw body text

from:
retrieval_text

Do not contaminate quote-capable source text by pretending injected section labels were in the original document.
Suggested:
text              = normalized source content
retrieval_text    = contextualized text used for embeddings later

or equivalent clean architecture.
16. Academic citations inside prose
Preserve in-text citations exactly enough for later citation verification:
(Smith, 2022)
Smith et al. (2023)
[14]

Do not remove them during normalization.
Do not resolve them in RAG-007.
Do not parse the bibliography into a citation graph yet.
17. Reference sections
Detect References, Bibliography, or equivalent sections using existing structural signals plus conservative patterns.
Chunks from reference lists should be tagged:
content_type = REFERENCES
is_retrieval_eligible = false

by default.
Preserve them in the corpus.
Do not delete them.
They may be used later for citation resolution or bibliography analysis.
Normal evidence retrieval must exclude them unless explicitly requested.
This is critical because a bibliography entry must not be retrieved as if it were a paper's substantive claim.
18. Abstract
Abstract text should be tagged:
ABSTRACT

Abstracts are retrieval eligible.
Do not merge the abstract blindly with the first body section if the parser can identify it.
An abstract may form its own chunk even if shorter than normal because it is a semantically complete unit.
19. Conclusions
Detect clear:
Conclusion
Conclusions
Discussion and Conclusion

sections where structurally available.
Tag:
CONCLUSION

They remain retrieval eligible.
Do not infer conclusions from prose semantics.
20. Tables
Tables must not simply be flattened into meaningless whitespace.
Preserve a deterministic textual representation.
Prefer something such as:
column A | column B | column C
value 1  | value 2  | value 3

or another explicit row/column representation.
Keep:
content_type = TABLE

and preserve page/section provenance.
Do not duplicate table text if RAG-004 already emitted the same text both as normal PDF blocks and as structured table data.
This duplicate issue must be explicitly tested.
21. OCR content
Respect RAG-005.
For pages where OCR is the effective text:
text_source = OCR

must survive to the chunk.
OCR prose may be retrieval eligible.
OCR-derived equations, figure labels and complex layout text must not be treated as verbatim-authoritative evidence.
Do not attempt OCR repair in this task.
If a chunk contains a mixture of native and OCR source items, record that fact.
Suggested:
text_sources = [NATIVE_PDF, OCR]

or equivalent.
22. Equations and figures
Do not attempt mathematical understanding.
Preserve extracted text when available.
Do not fabricate missing equations.
Figure captions may remain as contextual text if reliably identified, but do not treat arbitrary image OCR as normal prose.
Report limitations.
23. Corpus roles and evidence eligibility

Required behaviour:

  navigation/retrieval eligible
  NOT evidence

  retrieval eligible for supervisory decisions
  NOT scholarly evidence

  instruction context
  NOT scholarly evidence

  NOT evidence

Do not collapse these roles into one vector corpus conceptually.
Add explicit fields if needed:
retrieval_eligible
evidence_eligible
source_role
authority

Reuse existing RAG-001/RAG-006 semantics instead of inventing conflicting terminology.
24. future_chapters
This is especially important.
Chunks originating in:
data\future_chapters\

must preserve:
NAVIGATION_ONLY
NOT_EVIDENCE
PLANNING_GUIDANCE

or the equivalent existing policy representation.
They may later help locate ideas.
They must never silently support a scholarly claim.
25. summaries
Summary files may be chunked for navigation.
They must remain distinguishable from the original literature.
A later retrieval pipeline should be able to:
retrieve a summary
→
locate the original paper

but not cite the summary as the external evidence source.
Do not implement source-link resolution yet unless already available.
26. my_work
Preserve chunks from:
submitted paper
current paper
thesis

They are important for:
terminology continuity
consistency checking
avoiding unnecessary repetition
reusing the author's conceptual framework

But mark:
evidence_eligible = false

by default unless an intentional self-citation mode is added later.
Do not classify the user's own draft as literature evidence.
27. Chunk identifiers
Chunk IDs must be deterministic for unchanged input.
Prefer a stable ID based on:
document id/hash
chunk index
normalized chunk boundaries/content

Re-running RAG-007 on an unchanged corpus should generate the same chunk IDs and ordering.
Do not use a random UUID if that makes every reindex look like a completely new corpus.
28. Deterministic ordering
Chunk order must follow source order:
document
page
sequence
section

Running the chunker twice must produce byte-equivalent chunk payloads except for genuinely time-dependent metadata.
Prefer not to include a fresh timestamp in deterministic comparison output.
29. Normalized text versus raw text
Preserve enough information to audit transformations.
We do not need to duplicate huge raw strings in every chunk if the parser already retains raw document extraction.
But the system must be capable of tracing:
normalized chunk
→
parsed source item(s)
→
page/block/OCR source

Store source item identifiers / locators.
