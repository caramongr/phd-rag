PROJECT: PhD Academic RAG
TASK ID: RAG-016
TITLE: Add DeepSeek API as a manual cloud model alternative

Project root:

F:\phd-rag

IMPORTANT CONTEXT

RAG-015-REPAIR already provides:

- normal persistent chat
- saved chat history
- SQLite storage
- attachments
- large-context conversation
- local PhD corpus retrieval
- Local Qwen through Ollama
- Advanced RAG-009 to RAG-014 functionality

The UI and persistence now work.

However, qwen3.5:35b through Ollama is NOT reliable enough for real work.
The model periodically degenerates into token repetition such as:

"prediction aborted, token repeat limit reached"

and sometimes repeated words/tokens indefinitely.

This task exists ONLY to provide a reliable manually selected DeepSeek API
alternative so the user can continue working when local Ollama is unreliable.

DO NOT redesign the system.

DO NOT add another architecture layer unless absolutely necessary.

DO NOT touch unrelated RAG stages.

DO NOT add OpenAI.

DO NOT automatically fail over between providers.

DO NOT create another large testing project.

======================================================================
1. PRIMARY GOAL
======================================================================

Add DeepSeek API as another model choice in the existing SIMPLE CHAT.

The user must be able to choose which provider answers the NEXT message:

Local Qwen     🔒 Local
DeepSeek       ☁ Cloud

Local Qwen remains the default.

The same locally saved chat must work across both providers.

Example:

User message 1 -> Local Qwen
Assistant answer -> Local Qwen

User selects DeepSeek.

User message 2 -> DeepSeek
Assistant answer -> DeepSeek

User selects Local Qwen again.

User message 3 -> Local Qwen

All messages remain inside the SAME local conversation.

======================================================================
2. ABSOLUTE DATA-SAFETY REQUIREMENT
======================================================================

DO NOT LOSE EXISTING WORK.

Before any SQLite schema migration:

1. Detect the current chat database.
2. Make a timestamped backup copy.

For example:

data/chat/backups/chat-before-rag016-YYYYMMDD-HHMMSS.sqlite3

Do this only when a migration is actually required.

Migration must be ADDITIVE.

Never:

- recreate the database
- delete existing tables
- delete existing messages
- delete attachments
- reset chats
- regenerate conversation IDs
- clear existing chat history

Existing RAG-015 chats must open exactly as before.

If migration fails:

- stop startup cleanly
- leave original database untouched
- report the problem

======================================================================

Use the official DeepSeek API.

DEEPSEEK_BASE_URL

Default:

https://api.deepseek.com

API key:

DEEPSEEK_API_KEY

Never hard-code the API key.

Never:

- store it in SQLite
- put it in frontend JavaScript
- expose it through /api/chat/info
- print it in logs
- include it in error messages
- include it in screenshots
- include it in RAG-016-report.md

======================================================================
7. PER-MESSAGE PROVIDER SELECTION
======================================================================

Provider selection applies to the NEXT assistant response.

Do NOT permanently assign an entire chat to one model.

Store provider metadata with every assistant response.

For example:

provider = "ollama"
model = "qwen3.5:35b"

or:

provider = "deepseek"
model = "<actual DeepSeek model id>"

Existing old messages without provider metadata must continue loading normally.

The migration/schema must therefore tolerate NULL/legacy values.

======================================================================
8. MANUAL FALLBACK BETWEEN PROVIDERS
======================================================================

This is one of the most important requirements.

There must be NO automatic provider failover.

If Ollama fails:

DO NOT automatically send the user's PhD material to DeepSeek.

Instead:

- leave the user message saved locally
- show the failure normally
- allow the user to select DeepSeek
- click "Retry this turn"
- answer the EXISTING unanswered user turn with DeepSeek

Likewise:

If DeepSeek fails:

- keep the existing user message
- user may select Local Qwen
- Retry this turn
- Local Qwen answers that existing message

NO duplicate user message.

Example:

User message
    ↓
Qwen fails
    ↓
user selects DeepSeek
    ↓
Retry this turn
    ↓
DeepSeek answer

Database:

user
assistant

NOT:

user
user
assistant

Preserve RAG-015's existing failed-turn/retry logic.

Extend it to support a different manually selected provider.

17. ERROR HANDLING
======================================================================

Handle useful DeepSeek failures cleanly:

- invalid API key
- insufficient balance
- rate limit
- API outage / 5xx
- timeout
- connection failure
- invalid model

Do not expose huge HTTP traces to the normal UI.

Give the user a useful sentence.

Examples:

DeepSeek authentication failed.

DeepSeek rate limit reached.

DeepSeek service is temporarily unavailable.

DeepSeek request timed out.

Do not hide the underlying error from debug/logging, but redact secrets.

Never include DEEPSEEK_API_KEY in an error.
